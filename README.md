# 裁纸师工作台（Flask + SQLite + Docker Compose）

从一张印张上，按“贯穿整张纸片的横/竖 Guillotine 切刀”尽量多地裁出四边与画框完全重合的完整版画。
支持录入纸张与最多 12 幅互不重叠的矩形画框、给出最多还能裁成几幅及逐刀切序、
登记真实落刀（允许切偏）后按剩余纸片重新排程，并把进度持久化到 SQLite。

- 坐标：整数毫米，原点在纸张左上角，`y` 向下；画框用 `x, y, 宽 w, 高 h`。
- 刀缝按 **0** 计算。
- 横切 = 水平线，登记 `y`；竖切 = 垂直线，登记 `x`。
- 只有当某张纸片的四条边与某幅画框四条边**分别重合**时，该纸片才记为成品。

## 功能

1. **录入与校验**：纸张宽高、≤12 幅画框；整数校验、越界校验、正面积重叠校验（允许边贴边）；
   首页有动态表格和实时 SVG 预览；无 JS 时原生表单也可提交（错误返回 422 并回显）。
2. **最优排程**：记忆化递归 DP，输出
   - 当前各剩余纸片上“最多还能裁成几幅”及总数；
   - 达到该数量的完整切序，逐刀标明**纸片（编号/临时路径标签与坐标范围）、方向、位置**；
   - 每刀会切到并舍弃哪些画框、最终成品落在哪个临时纸片标签。
   - 优化目标按字典序：① 成品数量最多 → ② 成品总面积最大（同数量时优先舍最小画）→ ③ 刀数最少。
3. **实际落刀登记 + 偏刀续排**：登记真实刀位（可与推荐不同，记录偏差），
   立即把纸片分成两个子纸片、把被刀穿过内部的画框标记为 `ruined`、
   把四边重合的子纸片/画框标记为 `finished/done`，然后基于真实剩余纸片重算。
4. **三类拒绝（进度原样保留，不写 cuts/pieces）**：
   - 纸片已裁过并分成两片（`already_split`）；
   - 纸片已是四边重合的成品（`finished`，含状态滞后的几何兜底）；
   - 刀位不在纸片严格内部（`outside`，贴边 `pos==x0/x1` 或越界都拒）。
5. **持久化**：SQLite 四张表 `jobs / frames / pieces / cuts`；
   登记用 `BEGIN IMMEDIATE` 事务；外键级联；提供“重新开始”和删除印张。
6. **可视化操作页**：按比例 SVG 画出纸张、当前纸片（#编号）、画框状态、带序号的推荐刀线；
   统计卡、切序列表、登记表单（“填入登记”一键带入推荐刀位，可改偏）、当前纸片树、落刀记录。
7. **部署**：`Dockerfile` + `docker-compose.yml`（命名卷 `/data` 持久化 SQLite，带 healthcheck）。

## 用 Docker Compose 启动（推荐）

```bash
docker compose up --build
# 打开 http://localhost:5000
```

SQLite 文件在容器内 `/data/cutting.db`，由命名卷 `cutting-data` 持久化；
`docker compose down` 不丢进度，加 `-v` 才会删卷。

## 本地直接运行（不用 Docker）

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
CUTTING_DB=./cutting.db python app.py        # http://127.0.0.1:5000
# 或 gunicorn --bind 0.0.0.0:5000 app:app
```

运行测试：

```bash
python -m unittest discover -s tests -v
```

## 算法说明

对每张当前活纸片 `R` 独立求解。状态就是矩形 `R`（当前待排画框集合在一次规划内固定，
几何包含即可确定）：

- 若 `R` 与某待排画框四边重合：得 1 幅、0 刀；
- 否则枚举严格位于 `R` 内部的候选刀位——只取内部各画框的 `x0/x1`（竖）、`y0/y1`（横）。
  最优解的有用刀位总能挪到某条画框边而不恶化左右分组，故无需枚举每毫米；
- 刀后两子矩形递归，目标向量 `(数量, 成品面积, -刀数)` 取字典序最优；
- 被刀穿过内部的画框不被任何子矩形完整包含，等价于被舍弃/切坏。

复杂度对 ≤12 框非常小：单纸片可能的边界组合至多约 `(2n+2)^2` 个矩形状态，
每状态枚举 `O(n)` 刀位。

## 内置“必须舍弃小画”示例

首页点 **“必须舍弃小画：风车式五画（100×100）”**：

| 画框 | x,y,w,h | 面积 |
|---|---|---:|
| A 大画 | 0,0,70,55 | 3850 |
| B 大画 | 70,0,30,72 | 2160 |
| C 大画 | 15,72,85,28 | 2380 |
| **小画 D** | 0,55,15,45 | **675** |
| E 中画 | 15,55,55,17 | 935 |

五幅恰好铺满 100×100，且是非切片“风车”布局：任意贯穿竖线都严格处在某幅画的
x 区间内、任意贯穿横线都严格处在某幅画的 y 区间内，所以**不存在不切到任何画的第一刀，
5 幅不可能全出，最多 4 幅**。实测排程第一刀为 `#1 横切 y=72`（该刀穿过小画 D，将其舍弃），
随后 4 刀救出 A/B/C/E。

补充（已用求解器逐一验证）：单舍 A/B/C/D 都能得 4 幅，单舍 E 只能得 3 幅；
在所有“4 幅”方案中，舍 D 保住的总面积 9325 mm² 最大，因此第二目标唯一选中“舍小画 D”。
若只看数量，舍 A/B/C 也是并列最优——这是刻意保留的透明取舍，不是漏算。

  重叠与 >12 拒绝、三类登记拒绝、偏刀重排、重启级持久化、reset、表单 flash 流）。
- 真实启动 Flask（`python app.py`）后用 HTTP 走网页同一路由：
  - `POST /samples/pinwheel` 建单，操作页含“最多还能裁成 4”，`plan.json` 给出 5 刀，首刀 `H y=72`；
  - 表单登记 `H pos=100`、`V pos=-3`、`H pos=0` 均被拒，flash 显示“刀位不在纸片 #1 内部…
    登记已拒绝，进度未改动”，库中 cuts 仍为 0；

    页面提示“相对推荐刀位偏了 +2 mm”“此刀穿过并切坏：C 大画、小画 D”，

  - **持久化**：杀掉进程、用同一 SQLite 文件重启服务，`/jobs/1` 仍显示 3 成 2 坏、规划为 0；
  - **成品拒切**：建 40×30 满版画框，根纸片自动 `finished`，对其下刀返回 409 `finished`；
  - 第二个示例（三画宽边）实测**良性偏刀**：推荐 `V20` 实切 `V18`（偏 −2，未伤画），
    重排自动在 #3 上补 `V20` 修边，跟随完 8 刀后 3 幅全成；

  - `gunicorn app:app`（Dockerfile 的启动目标）在 5057 端口实起实测 200/建单/规划正常；
  - `node --check static/*.js` 语法通过；所有 Python 文件 `py_compile` 通过；
    `docker-compose.yml` 经 PyYAML 解析通过。

## 缺项与限制（如实说明）

1. **本环境没有 docker / docker compose 可执行程序与守护进程，因此 `docker compose up --build`
   未能在这里真正跑一遍**；已验证 compose YAML 合法、Dockerfile 的 gunicorn 启动目标可正常服务。
   首次在有 Docker 的机器上构建时仍可能遇到网络拉镜像/装包问题。
2. 本环境无 Chromium/Playwright/Puppeteer，**没有做真实浏览器像素截图/点击**；
   网页是通过真实 HTTP 服务 + 返回 HTML 文本核对、并用 `node --check` 检查 JS 语法来验证的，
   浏览器内的实际点击与 SVG 视觉效果未由人工目视确认。
3. 实际落刀位置同样只接受**整数毫米**；不支持 `72.5` 这类小数偏刀（题目约定整数 mm，
   若现场需要 0.1mm 可把坐标改成整数“丝米”或引入 Decimal，几何比较需一并改造）。
4. 规划只把“画框边坐标”作为候选刀位（有最优性论证），不会主动给“纯浪费区”安排无意义刀，
   但登记时允许对不含待排画的纸片任意下刀。
5. 面向单个裁纸工位：compose 固定 1 个 gunicorn worker；多 worker/多机并发虽有
   `BEGIN IMMEDIATE` 兜底，但未做压测。没有用户/权限体系。
6. 没有做撤销单刀（只能整单“重新开始”）、刀缝宽度/刀具补偿、旋转画框等扩展。
